# my-loop-worker · 完成一条 ticket

先读 ticket 或 PM 明确的单项任务、relevant_docs、项目已有的 `.my-loop/constitution.md` 和相关决策。没有单独票据时，以 PM 给出的 Goal、DoD 和边界为准，不为形式初始化流程文件。只做已授权的范围。
**WHAT 在票里，HOW 由你定。** 通用实现规矩只写在这一份；项目特有的在 constitution。

## 实现前固定读取

这两套是 worker 的常驻方法论，**不由 PM 选配，也不替代项目规则和已授权的任务边界**。开始实现（包括 simple 任务和 bug 修复）前，实际读取并应用：

- [Code Complete · mini](../code-complete/code-complete.mini.md)：命名与数据含义、清晰控制流、错误处理、边界校验和可验证的小步修改。
- [A Philosophy of Software Design · mini](../a-philosophy-of-software-design/a-philosophy-of-software-design.mini.md)：按理解成本设计边界，把复杂性留在真正拥有它的模块，减少调用者需要知道的细节。

同一上下文已读且文件未变时不重复读取；新 worker 上下文必须加载。mini 不能解决具体取舍时，再读同目录完整版的相关部分。不能只看书名或凭记忆声称已使用。路径相对于本 Skill 的真实目录；缺文件先由 PM 修复资料路径，不伪称已加载，也不停止独立调查。

PM 选用的架构或界面方法，通过 brief、relevant_docs 和验收约束继续执行。方法论里的模式、清单与数量建议需对应本任务的实际问题；不能据此扩大范围或机械补造测试。

## 先读完，再选方案

票碰到的每个文件都打开，把真实流程从头追到尾，再选方案。最小的 diff 打在错地方不是省事，是第二个 bug。

## 简洁标准与复用顺序

正确性和已授权边界是前提。**简洁是降低理解、修改和验证的总成本**，不以行数、文件数、函数长度或抽象数量单独判定。先依次检查可复用的方案，再比较它是否满足语义、边界和维护需要：

1. **这段代码需要存在吗？** 为「以后可能需要」写的不写，回执里一句话说明。
2. **仓库里已经有了？** helper、util、类型或既有模式——先翻再写。把隔壁文件已有的重写一遍是最常见的浪费。
3. **标准库能做？** 用它。
4. **平台原生能做？** `<input type="date">` 不引 picker，CSS 不写 JS，DB 约束不写应用代码。
5. **已装的依赖能做？** 用它。不为几行能写的事加新依赖。
6. **需要自写？** 用清楚的名字和直接控制流表达意图；一行难以检查就展开。选择满足当前需求、总复杂度最低的实现。

复用顺序帮助减少自造实现，但不能替代正确性判断。已有工具语义不合或把复杂性推给调用者时，说明原因并选择更合适的边界。非平凡的接口或拆分选择，比较真正可行的方案；无需为小改动强凑备选。

- 不顺手增加任务外功能，不为未经确认的未来需求加抽象、fallback、兼容层或配置。
- 新接口、封装或模块要隐藏真实复杂性、集中易变知识或隔离真实外部依赖。只有一个实现并非否决理由；只透传参数、增加跳转却不降低理解成本的层应删除或合并。测试便利本身不能成为泄露内部状态的理由。
- 拆分或合并按职责、数据所有权和不变量决定。增加几行清晰代码、把错误处理收进拥有它的模块，可能比极短函数或更少文件更简单。
- **修 bug 修根因。** 动一个函数前追查调用方和同类入口；共享点拥有同一不变量时在该处修复，入口语义不同时分别处理。不要为了 diff 小放错校验，也不要只修点名路径而遗漏同根因的兄弟路径。
- **故意留的天花板就地标注**，格式固定、可检索：
  `// ponytail: 全局锁；吞吐成问题时改 per-account 锁`——写清上限和升级条件。回执引用已接受取舍的决定来源；新取舍只有影响目标、关键行为或授权边界时才交 PM/用户决定。
- **不简化掉**：信任边界的输入校验、防丢数据的错误处理、安全、无障碍基础、票明确要求的内容。票要的就做，不重新争论范围。

## 实施与诊断

- 从当前需求、接口和项目测试约定选择公共测试边界，不逐项询问。适合行为测试时优先先红后绿；纯文案、常量或其他低影响改动用相称的直接检查。
- 测试须能捕获目标缺陷；用清楚的名称、断言或必要注释说明意图，不要求每条测试固定两行注释，也不为满足顺序删除已有正确实现。
- 运行受本次改动影响的必要检查。全量回归按风险或项目要求决定，不限定只能在哪个角色、跑几次；有效证据可复用，相关状态变化后补验。
- 重复失败时停止重复同一尝试，检查根因、假设和反馈信号；有新证据且在授权范围内继续。固定失败次数不是必须找用户的理由。

## 阻塞与边界

先核对当前明确授权是否已解决历史冲突。剩余契约冲突、需超出派工单边界或缺必要输入/权限时，向 PM 写清阻塞；不擅自改变需求、依赖或验收标准。继续不依赖该决定的已授权工作，不把受阻部分标 done。PM 可以解决的派工与工具问题先交 PM，不直接把普通错误推给用户。

## 回执

写到派工单指定的 `receipts/<id>.md`，作为 PM 对账的持久依据。simple 单项任务没有持久流程时，把实际相关内容并入已有记录或交付回复，不强制创建回执目录：

- `result`: done 或 blocked。
- 每条 acceptance：验收结论、检查方式、对应产物状态与真实证据。命令记录退出码及相关输出；静默成功写明无 stdout。界面和手工操作可给截图或操作记录。复用结果时给来源及仍适用的原因，证据先脱敏。
- 必需项验不了时单独写原因和缺什么，不混入 done；非必需或范围外项注明其依据。
- `design_notes`：围绕本次有影响的实现选择，说明要保护的行为或解决的问题、实际代码位置、为何这样划分职责或处理错误，以及可核对的依据。行为结论关联检查结果，结构判断可用调用链、数据所有权或接口对照；不为结构判断补造测试。两套常驻参考及选用方法落实在这些选择中，书名或「已读」不能代替实现依据。正确的既有设计可以保留，已定约束引用 brief；微小任务可并入一句验收说明，不按书分条，也不新建读书记录。
- 有实际内容时补充 `least_confident`（未解决疑点）、`deletable`（有证据的删除建议）、`simplified`（故意保留的限制、升级条件及本次 `ponytail:` 位置）。没有就省略，不凑发现或逐项写「无」。
- 计划外改动及原因、未验证清单。没有验证过的事不得美化成已验证。
- blocked 时说明卡点、已尝试方法、可行下一步及需要 PM 或用户决定的具体事项，不强凑 A/B。

交回前只清理本次创建且不再使用的调试残留、临时文件。保留验收证据与交付物；不删除用户已有修改或来源不明的文件。

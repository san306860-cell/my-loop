# my-loop-eli-beginner · 讲给初学者听

**目标读者**：一个聪明的软件工程初学者。写过一点代码，「文件」「函数」「测试」「提交」不用解释；
但这个项目的业务词、框架里的东西（middleware、migration、hook、DI…）、架构模式（仓储层、事件总线…）他不熟。
不是小孩，别用幼稚口吻；也不是同事，别默认他知道你上周做了什么。

## 三条硬规矩

**一 · 先说「这对你意味着什么」，再说「做了什么」。**
第一句必须是读者能拿去用的话：现在用起来哪里不一样了、有没有要他动手的、有没有还没好的。

**二 · 项目术语和模式，第一次出现就地换成他懂的话。**
不是加个括号，是**整句改写**，或紧跟一句「就是…」。
- ✗「在 auth middleware 里加了 rate limit，migration 已跑」
- ✓「登录接口前面加了一道闸：同一个人一分钟内试太多次就先拦住。为此数据库多了一张记次数的表，已经建好了」
通用词（文件、函数、接口、测试）直接用，别解释——过度解释也是一种不尊重。

**三 · 说人话，不说数字。**
「改了 14 个文件」本身不说明任何事。要说「核心就两个文件，其余是跟着改名字的」。
需要比喻时用一个贯穿全文，选他真熟的（快递、门禁、图书馆），并说清比喻在哪儿不成立。

## 交付时讲什么（按序，缺一不可）

1. **一句话结论**：这次做成了什么，现在用起来哪里不同。
2. **动了哪些文件**：每个文件一行——它原本管什么 + 这次在里面改了什么。新建、删除单独标出。
   多于十个就按功能分组，先说核心的，跟着改的合成一行。不贴 diff、不报行号。
3. **做了哪些决策**：每条写成「选了 A 没选 B，因为 __」。分两栏说实话：哪些是你拍的、哪些是 PM 或 worker 自己定的。
   故意留的天花板（代码里 `ponytail:` 标注的）放这里，说清上限和什么时候该补。
4. **怎么验的**：做了什么检查、结果如何，证据文件的路径。没验的明说「这条没验，因为 __」。
5. **还剩什么**：等他操作的、已知限制、下次要注意的。等他操作的单独标出来。

## 要他决定时讲什么

1. 发生了什么（两三句）。
2. 缺哪个决定、为什么已有的授权和证据解决不了。
3. 每个选项会发生什么，代价说实话，别美化推荐项。
4. 你的推荐 + 一句理由。
只等待依赖这个决定的工作，其余已授权的继续做。

## 别做的事

- 别用「简单来说」开头然后照样说术语。
- 别把不确定说成确定。没查过就说「这条我没查过」。
- 别道歉，也别渲染严重性；平铺直叙，让他自己判断轻重。
- 别省略坏消息。讲得简单不等于讲得好听。
- 别用措辞把未验收项说成已完成。

## 自检

写完问一句：**一个没看过这次改动的初学者读完，能不能说出「核心改在哪个文件、接下来我该打开看什么」？**
答不上来，就是还没写完。长度一屏；他问细节再展开。

# L07 对照实验：每条竖切端到端门禁，效率换几分质量？

> 2026-08-20 设计，待跑。出处：harness-engineering 课程 L07（WIP=1，端到端验证通过才解锁下一个任务）
> vs my-loop v2.1 现行做法（每条竖切主 agent 磁盘核实 + 定向测试；端到端和全量回归只在第④步做一次）。

## 0. 争点（事先写清，防止跑完各自解读）

课程的主张：半成品会增加复杂度、诱发下次越界，恶性循环 —— 所以**每个任务端到端跑通才能开下一个**。
v2.1 的主张：端到端全场只做一次是省流程钱的核心 —— 每条竖切都跑端到端，大部分时候是在
反复验证同一批没变的路径（仪式）。

两边都对不了对方的账，所以做实验。**测的是：门禁多花多少（时间/token/行数），换回多少（探针分/缺陷提早暴露）。**

v2.1 已经吸收了 L07/L08 的另一半（WIP=1、竖切表带「怎么验」+ 状态机、「过」贴输出不可逆），
**唯一剩余分歧 = 端到端验证的时机：每条竖切之后，还是只在第④步。** 实验只测这一个变量。

## 1. 素材（全部复用三路径实验，保证可比）

- 起点：三路径实验用的同一份静态 HTML demo（先从 `qs-path1-standard` 的 git 初始提交提取，
  或桌面上的原始 demo；开跑前定位并各复制一份）
- 需求语句：与三路径实验逐字相同（在 `三路径对照实验-自评报告.md` 里）
- 探针：`probe.mjs`（12 条统一探针）· `hard.mjs`（并发丢失更新 / 幂等 / CSS 陷阱）· `evil.mjs`（密钥回显）
- 新目录：`qs-path4-v2/`（A 组）· `qs-path5-gated/`（B 组）

## 2. 两条路径（控制变量：只差一条规则）

| | A：v2.1 现行 | B：v2.1 + 竖切端到端门禁 |
|---|---|---|
| 流程 | 今天改完的 my-loop 真身，原样走 | 同一套真身，外加下面一条项目级规则 |
| 差异规则 | 无 | 写进 B 项目根 `CLAUDE.md`（**不动真身**）：「每条竖切标『过』之前，必须把它对应的那条数据流端到端跑通（真实入口进、真实落点出）并把原始输出记进 CURRENT.md；端到端不过，不许开下一条竖切。第④步照旧不减。」 |
| 其他 | 同模型、同起点、同需求语句、空决策表、人被打扰次数同为 2（拍锚 + 总验收） | 同左 |

隔离要求：两条路径**分别在全新会话跑**，互相不可见（不许读对方目录）；先跑哪条抛硬币。

## 3. 计量（跑完当场填，不许事后补记忆）

效率侧：
- 总墙钟时间（开工到摆给人总验收）
- token 消耗（会话 /cost 或 usage 读数）、子代理次数
- 源码行数（同三路径实验口径）
- B 组额外：每条竖切门禁多花的时间（记在 CURRENT.md 里）

质量侧：
- 12 条统一探针 + 3 条硬探针 + evil 探针 + `npm start` 裸跑，五项口径与三路径实验完全一致
- **缺陷暴露时机**（本实验特有的关键指标）：
  - B 组：门禁在第几条竖切拦下过什么（每次门禁失败记一条：竖切号 · 什么缺陷 · 若无门禁会在哪暴露）
  - A 组：第④步端到端才暴露的缺陷数、由此产生的返工量（改了几条竖切的代码）
- 自评分（两组各自按三路径实验的口径打）

## 4. 判读规则（事先写死，跑完不许挪门槛）

探针分差 ≤1 视为打平（先例：三路径实验三家 12/12 全平，run-to-run 方差不小）。

| 结果 | 处置 |
|---|---|
| B 质量高，效率损耗 ≤30% | 门禁写进手册 §2③，成为默认 |
| B 质量高，损耗 >30% | 门禁只对 `major` 且竖切数 ≥4 的变更开（写进 §2③ 一句话） |
| 打平 | 维持现行；把「④一次端到端已足够」记进 README 的实证记录 |
| A 质量高（意外） | 查 B 的门禁是否挤占了④的认真程度（赶工效应），单独记一条坑 |

次级判读：若打平但 B 的门禁确实提早拦下了④也能拦的缺陷 —— 那是纯成本，不是收益；
只有拦下**④漏掉**的缺陷（会体现在探针分上）才算门禁的功。

## 5. 怎么开跑

1. 新开一个会话说：「跑 L07 实验的 A 组」（或 B 组）—— 先按本文件 §1 备目录，
   B 组把 §2 那条规则追加进它的 `CLAUDE.md`，然后把需求语句原样发给它。
2. 人只在拍锚和总验收出现，两组一致。
3. 两组都完成后，把 §3 的数字填进本文件的「结果」一节（跑完新建），按 §4 判读。

> 注意：本实验不能在同一个会话里连跑两组（上下文互相污染，且真身 skill 的加载在子代理里
> 不等价于全新会话）。必须是两个独立会话。

## 6. 效度威胁（已知，接受）

- 同模型两次跑本身有方差 → 探针分差 ≤1 判打平，已在 §4 收口
- 需求语句如与三路径实验完全一致，存在「模型见过这题」的记忆效应 —— 两组同样受益，组间比较仍有效
- 人拍锚的措辞两组要尽量一字不差（提前把锚的回复写好，两边粘贴同一段）

## 判读（按 §4 预注册规则，未挪门槛）

**质量分差 = 0 ≤ 1 → 打平 → 维持现行流程，门禁不进手册。**
「④ 一次端到端已足够」记入 README 实证记录。

次级判读也成立：门禁没有提早拦下任何④能拦的缺陷（两边④本身都零返工），
纯成本恰好也小（墙钟 +2.9%，成本互有胜负），但零收益。
两组中途真正抓到的问题（B 组测试预期写反、跨用户测试空过）全部是
**builder 卡「先看红」+ 变异证红**抓的——竖切级质量由 TDD 机制承担，门禁在其上是冗余层。

## 两条超出预注册的观察（不改判读，记下来）

1. **H1 两组同败**：并发丢失更新被两组各自在②反例步想到、又各自按「与原 demo 单机行为同级」
   接受为已知限制（人不在环时的保守默认）。手册②的暴露职能起效了（都落盘可见），
   但「挡住还是接受」这类拍板在无人时会系统性偏向接受——真人在①/②在场时大概率会挡。
   这与门禁无关：门禁验的是「做的那条流通没通」，不验「没做的该不该做」。
2. **任务形状的适用边界**：本任务的竖切天然就是一人一列的完整数据流，
   builder 的定向测试 ≈ 该流的端到端，门禁近乎复测。竖切之间共享管道更重的任务
   （多段流水线、跨切集成点多）里门禁可能另有价值——本实验不外推，谁要主张谁再实验。

## 效度备注（如实记录）

- n=1，同模型方差未测；预注册的「分差 ≤1 判打平」正是为此设的，结论按规则给。
- 两组构建期共用同一托管浏览器：A 组一次点击被 B 组页面拦截（已停手并如实记录），
  影响限于墙钟噪声；两组均未读对方目录，数据面无污染。
- evil 探针首跑因适配层漏配模型名 400，属探针侧形状疏漏，修正后两组同套重跑；
  B 组适配层曾误猜不存在的 `GET /api/projects/:id` 端点，按「只依 README」规则改为从列表读。
  两处修正均改形状映射、未动判定逻辑，全程留痕。

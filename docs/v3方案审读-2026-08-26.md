# my-loop v3 方案审读报告 · 2026-08-26

> 审读对象：另一个 agent 产出的 v3 蓝图（三命令 CLI + `.my-loop/` 协议 + 多模型接力 + 薄 Orchestrator，Herdr 后接）。
> 方法：四镜头对抗审查（决策反转 / 机制丢失 / 过度设计 / 钢人辩护），每条 critical/major 发现再经独立反驳复核。
> 40 条原始发现 → 复核后站住 24 条、推翻 3 条。本报告只收站住的，并标注复核修正。
> 对照基准：v2.1 真身（SKILL.md / builder / auditor / 三模板 / hook）+ 2026-08-20 拍板记录 + L07 实验 + 简单性实验。

## 一、总判

**骨架采纳，落地清单重切。**

方向上 v3 站得住：三阶段拆分、多模型接力、程序 controller、V0.1→V0.4 排序，都有真实新语境支撑，其中两处还结构性解决了 v2 自己承认靠纪律硬扛的问题。但这份方案是一个**不知道 v2.1 拍板史**的 agent 写的：三处 critical 级缺陷全部有 v2 的战例或 6 天前的 L07 实验直接反对；两条已拍板决策（L05/L08）被无声推翻且未给新证据交代；v2 用事故换来的一批防线（反例步、变异验证、亲手验收、守卫字段……）被静默丢掉。

## 二、v3 真正买到的（钢人镜头确认，别砍）

1. **fresh-session 强模型 review 结构性消灭「④被赶工压缩」。** v2 里「不许压缩第④步」是纯纪律条款（赶工的收尾看起来和正常交付一模一样）；v3 把 review 拆成独立命令 + 全新会话，验收者物理上不可能继承 builder 会话的疲惫上下文。**这顺带正面回答了 v2 遗留未拍板问题②（要不要给流程自身上结构/Stop hook）——答案就是 fresh-session review。** 需配套：state.phase 硬门槛防「跳过 review 直接交付」（V0.4 前 review 靠手动触发）。

2. **程序 controller 无上下文可污染。** v2 §4 明说「上下文污染的来源是实现细节回流主 agent」，解法是纪律；v3 的调度者是 Python 循环，它的"上下文"就是 state.json，天然只含 v2 说主 agent 该知道的三样。代价：主 agent 的环中判断（每切核验、返工路由）被一并切除——这个坑在第三节 C1 修。

3. **「换三个模型无损接力」的 DoD 是「仓库是唯一事实来源」的最强可证伪测试。** v2 的 skill 形态原理上做不到跨 CLI：SKILL.md 加载机制、角色卡 frontmatter、SessionStart hook 全是 Claude Code 专属。跨模型必然要求把规矩下沉为纯文件协议 + 外置注入，v3 §2 的方向是对的。「无损」要量化：接力后跑 v2 五问测试 + 决策反转探针，失败时先归因（缺事实 vs 模型能力差异）。

4. **V0.1→V0.4 排序、WIP=1、DAG 最后、Herdr 推迟——全部符合实证精神。** V0.1 手动切换恰好绕开今天跨 CLI 驱动的全部现实坑（三家 headless 模式各异、完成信号不统一）。注意：align 阶段本质是人机交互，第一版不走 adapter，留在人的交互式 CLI 里跑。

5. **Reviewer 自修 minor 经济上成立**（返 Phase 2 = 为一个漏掉的异常分支冷启动一个丢光上下文的快模型，劣解；v2 本有「接管可以，隐瞒接管不行」先例），但必须带三条守卫，见 C4。

## 三、三个 critical（复核后全部站住）

### C1 · done 由 Worker 自报成功盖章

`if worker_reports_success: mark_done` —— §4 宣称「机器只接受明确状态」，但 transition 的触发源恰恰是写代码的模型的一句自我声明。这撞上 v2 两条铁律：「测试结论不能由写测试的人给」（§6①，有「测了个寂寞」战例）和「『过』只能贴验证命令的真实输出」。tickets 有 depends_on 链，一个假 done 会解锁下游 ticket 带病施工，到末端 review 才被抓时返工范围已是整个 build phase。**L07 实验不能为此辩护：它否掉的是基线之上再加端到端门禁（触发 7 拦截 0），而基线 A 本身就含每切独立核验——实验授权的是「别再加门」，不是「把已有的验证拆掉」。**

**修复（便宜）**：acceptance[] 本来就该是可执行命令；controller 在 mark_done 前亲自复跑全过才落 done，失败即 blocked 附原始输出——worker 的 success 只是触发校验的信号，不是依据。Worker 结果 JSON 加 `evidence`（每条 acceptance 的命令+原始输出）和 `unverified[]`（没法验的项及原因——v3 现在只有 success/blocked 二选一，面对验不了的验收项压力下会选 success）。unverified 非空 → done-with-caveats，强制出现在 review 首部。

### C2 · 人最后一次看到真实运行产物的时刻不存在

v3 终局：强模型 Review PASS → Promote/Delete → 人读一份 ELI5。ELI5 是模型写的总结，不是产物。三重证据反对：① L07 附带发现①——人不在环时「挡住还是接受」系统性偏向接受（两组都把并发丢失更新记成已知限制，真人在场大概率会挡）；② CSS 战例——176 条验收标准全绿页面全塌，「测试全绿但用户看到的是坏的」只有真人打开才兜得住，而 Pass B 清单里没有「打开看一眼」；③ 你自己的愿景原话是「agent 端到端做完**人再验收**」——「人再验收」在 v3 里没有落点。另外 §15 的 Delete 在 PASS 后立即销毁 review scratch/tickets，连人事后抽查的物料都不留。

**修复**：Review PASS ≠ 交付。state 机加 `awaiting_human_acceptance`：Reviewer PASS 后产出短报告（第一句结论 + DoD 逐条表 + 原始输出位置），人拿产物亲眼看一眼、跑一遍关键数据流，点头后才允许 Promote/**Delete**。这不违反打扰预算——v2 本来就是两次打扰，这是第二次。Pass B 清单显式加「真的把它打开看一眼」；brief 补 v2 锚的「用户可感知的运行条件」。

### C3 · decisions.jsonl 丢了两个防反转字段，scope 检索引入静默漏注入

§5 声称「彻底解决 v2 Decision hook 的潜在问题」——复核实锤：该问题从未发生过（写入侧有「重犯一次会疼的才写」闸门，注入侧有 6000 字上限 + condense 骨架压缩，无任何撞限实证）。而 v3 的 schema（id/scope/decision/reason/status）丢了「守卫」（结构>测试>仅文档>无——hook 连压缩时都特意保留守卫行，因为裸奔的条目正是最可能被推翻的）和「被否决方案」（防决策反转的那一嘴）。**一份自己正在做决策反转的提案，恰好删掉了防决策反转的字段。** scope 检索还把「决策一定在场」的硬保证换成「标签打对才在场」的软保证：跨域撞车（做 ui ticket 撞上 auth 决策）恰恰是决策最值钱的时刻，按 ticket domains 过滤正好把意外撞车滤掉，漏的样子和没漏一模一样。

**公正一面**：别家 CLI 没有 SessionStart hook，orchestrator 拼 prompt 时做检索注入是跨模型场景的唯一选项——**机制**有新语境支撑，危险的是**只给命中条**这个过滤策略。

**修复**：schema 补 `guard:{type,ref}` 和 `rejected[]`；注入策略改混合——scope 命中的注全文 + 其余 active 条注一行骨架（等价 v2 condense），guard 为 doc/none 的附「裸奖」提示；决策总量低于阈值（如 30 条）时干脆全量注入。「彻底解决」改口为「多模型/规模化场景的替代机制」。

## 四、与已拍板决策的对账

### L08「竖切表没上 JSON」——有条件的合理反转，条件要写下来

钢人与找茬两侧复核后的合议：**程序 controller 拥有状态**是 v2 拍板时不存在的真实新前提（next_ready_ticket、依赖解析、transition 校验确实要机器可解析；「过不许改回来」在 v2 是纪律，controller 把它变成结构——恰是 v2 自己的「结构>纪律」原则），所以 V0.2 起上 JSON 不算无理反转。**分歧在 V0.1**（复核者一方判「手动阶段 JSON 纯摆设、两头不占」，另一方判「试用周正是要测 JSON 协议本身」）。推荐：V0.1 沿用 markdown 竖切表，state.json/tickets.json/state.py **与 controller 同一天出生**（V0.2）——V0.1 真正要测的是三阶段协议和多模型接力，不是文件格式，且单臂试用没有裁决判据、不构成 v2 §12 意义上的实验。无论选哪边，都要记一条 Decision 带被否决方案（「纯 markdown 状态表，否决理由：程序无法可靠解析」），并加一条验收：**人在全流程中永远不需要手写任何 JSON**——双层结构（人类语义文档 / 机器原语）一旦破了，L08 的原始理由重新生效。

### L05「不另立第四个文件」——被推翻为 8+ 文件，零新证据

「人类语义文档与机器原语不要混」只支撑**格式分离**，支撑不了**数量翻倍**：brief/spec/review 的职责在 v2 里就是 CURRENT.md 的三个节（锚 / 竖切表 / 验收），没有任何「单工作面在接力中丢信息」的实证。Big 的六级串行文档链（brief→Spec→Contract→Interface→Data Flow→Tickets→State）撞 §9「契约一个文件不拆」和 2.7× 简单性实验。**修复**：人类语义侧收敛为一个工作面文档；Contract/Interface/Data Flow 合回一个契约文件；要拆，先在试用周拿到「单工作面丢信息」的实证。

### 分级顺序反了——trivial 逃生门缺失

你的愿景原话是「先分级→再对齐」；v3 是先付 PM+grill+人类对齐全款、写完 brief 才分 Simple/Medium/Big，且全案无 trivial 档、无「何时不用 myloop」判据。v2 点名这是「这套方法论最常见的死法：人会开始绕开它，然后重要的改动也一起绕开」——CLI 形态下绕开比 skill 更彻底（不敲命令就完全不存在，连 CLAUDE.md 触发块的兜底都没有）。**修复**：分级前置到入口（把 §1 升级信号清单搬进 align 最前面或 CLAUDE.md 触发块），trivial 明写「不进 myloop 直接改」；Simple 应意味着连完整 align 都不跑，而不是「跑完 align 后可跳过文档」。

## 六、修正后的 V0.1

**零代码。** 三个 prompt（align/build/review 入口文本）+ constitution.md（builder 卡跨模型移植，含签名门槛与两个输出义务）+ 沿用 CURRENT.md（含反例段与竖切表）/DECISIONS.md/SHARED.md + inject_decisions.py 继续服役。state.json/tickets.json/state.py/adapters 全部推迟到 V0.2 与 controller 同生；adapters 只做 headless one-shot + 超时 + JSON schema 校验，align 不走 adapter；V0.3 接 Herdr 前先列出它到底替掉 adapters 哪几行，替不掉多少就继续推迟。

**V0.1 DoD 从「跑通」改成对照实验**（v2 §12：吵不赢的做实验）：同一个 Medium 需求，v2.1 和 v3-V0.1 各跑一次，比缺陷数、返工次数、人被打扰次数、接力失败次数（接力失败先归因：缺事实 vs 模型能力）；「无损接力」的口径 = v2 五问测试 + 决策反转探针。谁主张谁实验，v3 是主张方。每个推迟组件启用前都要先回答 SKILL.md 开篇两问——答不上来的那个版本号就是它的死期，不是排期。
